# 06 · 数据同步：两套互不相干的「同步」

> 这是全项目最容易误解的一章，先把最重要的事实说在前头：**本项目有两套互不相干的同步系统**，共用一个设置页，但代码、协议、状态存储完全独立。
>
> - **(A) WebDAV 同步**（本分支重点维护）：`src/core/sync/`。把歌单、设置、自定义音源序列化成三个 JSON 文件，放在用户自己的 WebDAV 服务器上，多台设备之间做增量同步。
> - **(B) 同步服务器**（上游 LX Music 自带）：`src/plugins/sync/` + `src/store/sync/`。连一台自建的 LX 同步服务器，走 WebSocket 长连接实时同步歌单与「不喜欢」规则。
>
> 下文凡未特别标注的，都是在讲 (A)。

---

## 6.1 (A) WebDAV 同步：文件地图

| 文件 | 职责 |
|---|---|
| `src/core/sync/webdavSync.ts`（1005 行） | 子系统心脏：主同步流程 `triggerWebDAVSync(isManual)`、四个手动全量覆盖入口、变更标记 `markListsChanged` / `markSettingsChanged`（+3 秒防抖调度） |
| `src/core/sync/opQueue.ts` | 未同步歌单操作队列：`loadOperationQueue`、`whenOperationQueueReady`、`logOperation`、`getOperationQueue`、`clearOperationQueueSnapshot` |
| `src/core/sync/webdavFailover.ts` | 故障转移：`runWithWebDAVFailover(task)`、错误分类 `isFailoverWorthyError`、轮换 `rotateToWorkingProfile` |
| `src/core/sync/syncHelpers.ts` | 数据抓取与过滤：`getAllDataForSync`、`filterSensitiveSettingsForSync`、`COOKIE_SETTING_KEYS` |
| `src/core/webdavMusic/profiles.ts` | 多服务器档案（故障转移的候选池来源），见 [05 章](05-WebDAV子系统.md) |
| `src/utils/webdav.ts` | 兼容层：同步层经它访问远端文件原语 |

操作队列的**入队点不在 sync 目录里**：`src/event/listEvent.ts` 在每个本地歌单事件（create/remove/update/music_add 等共 12 类）里先 `logOperation` 再 `markListsChanged`；远端同步来的操作（`isRemote=true`）不入队——这是防「同步回声」的关键。

UI 在 `src/screens/Home/Views/Setting/settings/Sync/index.tsx`（凭据、开关、测试连接、立即同步、四个手动按钮 + 进度条、上次歌单同步时间）；同页下半部挂 (B) 的开关与地址历史。

## 6.2 同步的三个文件与裁决策略

远端目录 = 设置 `sync.webdav.path` 归一化后的路径（默认 `/LX_Music/`）。

| 远端文件 | 内容 | 归属开关 |
|---|---|---|
| `playlists.json` | 歌单全量 + 可选的 playHistory / downloadTasks 附带字段 | `sync.webdav.syncLists`（自动同步时）；手动不受限 |
| `settings.json` | 过滤后的设置对象 | `sync.webdav.syncSettings`（`!== false` 才同步） |
| `user_apis.json` | `{ list: 音源列表, scripts: { id: 脚本文本 } }` | `sync.webdav.syncUserApis`（同上） |

统一信封格式（`wrapSyncFile`）：`{ version: '2', lastModified: <毫秒时间戳>, data: <载荷>, playHistory?, downloadTasks? }`。后两个键只出现在 playlists.json，且分别受 `sync.webdav.syncPlayHistory` / `sync.webdav.syncDownloadTasks` 控制。歌单载荷由 `isValidListsData` 守门：必须含数组型的 `defaultList / loveList / userList`，否则整段同步跳过。

**三类数据、三种裁决策略**——这是本子系统的核心设计：

### 歌单：时间戳判新旧 + 操作队列重放合并

- 本地基线是设置键 `sync.webdav.lastSyncTimeLists`。
- 远端更新（`lastModified` 更大）且本地有未同步变更（opQueue 非空 ∨ `listsChanged` 标志 ∨ 历史/任务有差异）时：把本地操作逐条 `applyListOperation` **重放到远端数据上**；成功则合并结果覆盖本地并回传云端。
- 重放抛错 = 真冲突：弹二选一对话框（云端覆盖本地 / 本地覆盖云端 / 取消）。
- 远端较新且本地无变更 → 纯下载覆盖；远端不新且本地有变更 → 纯上传。
- 同步成功后按**入口快照**清队列（`clearOperationQueueSnapshot`）：同步期间用户的新编辑不在快照里，会被保留——早期版本「整表清空」曾把同步窗口内的新编辑一起抹掉，这是快照语义的由来。

### 设置 / 音源：hash 判本地变化 + 时间戳 last-write-wins，无合并

- 本地是否改过，看内容 hash 与基线 hash 是否不同。设置的 hash（`hashSettingsForSync`）在 stringify 前先剔除全部 `sync.webdav.lastSync*` 元数据键——否则每次同步写基线都会改变 hash，形成自反馈 ping-pong。
- 两边都改了（远端时间戳更新且本地 hash 偏离基线）→ **本轮跳过、两边都不动**，每会话 toast 提示一次，留待用户手动取舍。不做自动合并是刻意的：设置没有安全的字段级合并语义。
- 首次同步（无基线）且远端文件无时间戳 → 同样跳过防误覆盖；无基线但远端有时间戳 → 放行下载并建立基线。

### 播放历史 / 下载任务：按 id 合并，本地优先

- `mergePlayHistory`：先铺远端、再铺本地（同 id 本地胜），按 `playedAt` 降序截断 5000 条。
- 下载任务落本地走 `adaptRemoteTasksForLocal`：只同步任务本体，保留本地的 `filePath / status / progress / errorMsg` 等运行态字段（上传侧由 `normalizeDownloadTasksForSync` 剥离本机绝对路径）。

### 附则

- **上传时间戳单调化**：`monotonicTimestamp(remoteTs)` 取 `max(Date.now(), remoteTs + 1)`，防时钟回拨或跨设备时钟差让刚上传的文件下一轮被「旧文件」滚回。
- **损坏自愈**：`safeParseSyncFile` 对解析失败/非对象的远端文件返回 null 并跳过本轮（不动本地），toast 给出恢复路径「用手动上传以本地覆盖」；自动同步场景每会话每类只弹一次。

## 6.3 敏感数据处理

`filterSensitiveSettingsForSync` 在**上传与下载落盘两头都过一遍**：

- 默认剔除：`common.wy_cookie`、`common.wy_serpapi_key`、`common.yt_cookie`、`common.tx_cookie`、`common.kg_cookie`、`sync.webdav.password`。
- `sync.webdav.syncCookies = true` 时四个平台 Cookie 放行（`wy_serpapi_key` 与 WebDAV 密码仍剔除）。
- **无条件剔除**：全部 `sync.webdav.lastSync*`（同步元数据）与 `sync.webdav.url / username`——服务器身份绝不跨设备搬运（一台设备的服务器地址同步到另一台只会把对方带沟里）。
- 设置下载是**合并语义**：底层 `updateSetting` 无法删键，云端没有的本地键会保留。下载后的基线 hash 按「合并后本地真实状态」重算，而不是远端值——否则 3 秒后防抖会把含本地残留键的合并态回传云端，污染还原点。

## 6.4 触发方式与一次自动同步的完整时序

触发源有三：歌单操作（经 `listEvent.ts` 入队 + `markListsChanged`）、播放历史变化（`core/player/playHistory.ts` 调 `markListsChanged`）、任意设置变更（`core/common.ts` 的 `updateSetting` 动态 import 调 `markSettingsChanged`）。三者汇入 3000ms 防抖 `debouncedSync`。

```
1. 变更发生：序号 +1（listsChangeSeq / settingsChangeSeq），防抖计时 3 秒
2. 防抖到期：按各开关与变更标志算本轮需求，无需求不跑
3. triggerWebDAVSync(false)：返回四态（2026-11-12 M-4/F1 后）——
   isSyncing 为真返回 'not-run'（防抖层据此保留标志、重新调度，不丢同步）；
   未配置（enable 关 / url 缺失）返回 'not-configured'（只留标志、不重调度，
   填好地址后经 mark 重新触发）；跑完成功 'ok'、跑了但失败 'failed'
   （失败保留脏标志，走 30s → 2min → 10min 指数退避重试，三档用尽后
   等下次变更再调度；新变更到来时若预算已耗尽则重置计数）
4. await whenOperationQueueReady()：等 opQueue 首次加载完成；
   加载失败 → 抛错中止本轮（防残缺队列在清队列时抹掉未同步操作）
5. 进入 runWithWebDAVFailover（failover 开启时先预检/轮换，见 6.5）
6. 歌单段：下载 playlists.json
   - 不存在 → 上传本地全量 + 快照清队列
   - 损坏/结构不合法 → 跳过歌单段（不清队列、不推进时间戳）
   - lastSyncTimeLists === 0 且云端有数据 → resolveFirstSync 弹窗二选一
     （下载覆盖本地 / 上传覆盖云端且历史任务先合并再传 / 取消）
   - 常规分支按 6.2 裁决：合并重放 / 纯下载 / 纯上传
7. 设置/音源段：syncSettingsAuto、syncUserApisAuto 依次跑；
   两者的错误收集第一个抛出（不内吞），使外层 failover 能感知连接失败
8. failover 回调若中途抛连接类错误 → 轮换服务器后整个回调重跑一次
   （首次同步/冲突弹窗在极端情况下会再弹一次，代码注释自认这是可接受的罕见代价）
9. finally 复位 isSyncing；防抖层按变更序号决定是否清标志
   （同步期间的新变更序号不同，不会被误清）
10. 失败时 toast 友好错误（friendlyWebDAVError 映射），原始错误进 webDAVLog
```

**生效方式**：歌单/历史/任务经事件即时生效；设置/音源是「下次读取生效」型——自动同步不弹重启提示，只有设置页手动下载（返回 applied=true）或「立即同步」前后设置快照有差异时才弹 `promptRestartAfterSync`，确认后走原生 `restartApp()`（bridge reload）。

**手动操作**（四个全量覆盖按钮）与自动流程共用守卫链：`checkSyncReady`（弹窗前查一次 + `runGuarded` 内再查一次，堵确认框停留期间自动同步抢跑）→ 确认框 → `runGuarded` 内套 failover → 分步进度回调 → 基线用**上传前快照**回写（防上传期间的新变更被误标已同步）。

## 6.5 故障转移（failover）

解决的问题：主服务器挂了，同步不要直接失败——自动换一台备用的试试。

- **候选池**：`profiles.ts` 的 `getFailoverCandidates()` = 已保存的服务器档案中除当前生效外的全部（按保存顺序）；档案总数 <2 时没有候选。当前生效档案的识别 `findActiveWebDAVProfile`：优先认持久化的 activeId（`@webdav_server_profiles_active_id`），且要求 url+username+password 与当前设置全等，否则退化为按三元组匹配任意一条。
- **触发条件**：仅设置 `sync.webdav.failoverEnabled` 开启时，`runWithWebDAVFailover` 包裹手动与自动两条同步路径。先**预检** `testConnection()`（读根目录，根 403 时改测同步目录，15 秒超时）；失败且错误「值得转移」→ 逐候选 apply + testConnection，首个通的留下（`sync.webdav.failoverNotify` 开时 toast 通知用户已切换）；预检过了但主流程中途再出连接类错误 → 再轮换一次并整任务重跑一次（不递归套娃）。全部候选不通 → 用进入前的快照回滚四个凭据键，抛原始错误给外层按普通同步失败处理。
- **切换的实现细节**：`applyWebDAVServerProfile(id, { silent: true })` 把候选写回 `sync.webdav.url/username/password/path` 并 `resetClient()`；silent 路径**直写 store 不标脏**——走普通 `updateSetting` 会触发 `markSettingsChanged`，等于切换本身再调度一轮注定失败的同步。档案的 `path` 字段随切换一起换（老档案无 path 时保留当前 path）。
- **可转移错误分类**（`isFailoverWorthyError`）：有 HTTP status 时仅 401/403/407/408/429/5xx；无 status 时认 `E_`/`NSURLError` 开头的 code、网络关键字（含中文「超时」）或 message 含 network 的 TypeError。**明确不转移**：404（在同步语义里是「文件不存在」的正常分支）、含「未配置」的错误、`SyntaxError`（云端文件损坏是数据问题，换服务器没用）。

## 6.6 持久化与设置键清单

**设置键 `sync.webdav.*`**：`enable`（总开关）、`url`、`username`、`password`（明文）、`path`（默认 `/LX_Music/`）、`syncLists`、`syncPlayHistory`、`syncDownloadTasks`、`syncSettings`、`syncUserApis`、`syncCookies`、`failoverEnabled`、`failoverNotify`，以及只存本机、被过滤器排除出同步载荷的**基线五键**：`lastSyncTimeLists`、`lastSyncTimeSettings`、`lastSyncSettingsHash`、`lastSyncTimeUserApis`、`lastSyncUserApisHash`。

⚠️ **默认值口径不对称，改代码时小心**：`syncLists` 在 `triggerWebDAVSync` 里按「undefined = 关」处理（但 UI 打开总开关时会顺手置 true）；`syncSettings` / `syncUserApis` 用 `!== false` 语义（默认开）。三类开关的默认语义不一样，是历史形成的，如实记录。

**独立存储键**：opQueue = `@sync_op_queue_v2`；档案 = `@webdav_server_profiles`、生效标记 `@webdav_server_profiles_active_id`。WebDAV 连接凭据不另存，运行时由 `client.ts` 单例从 `sync.webdav.*` 现读并按凭据指纹缓存 client。

## 6.7 (B) 同步服务器（上游体系）速览

代码在 `src/plugins/sync/`，运行时状态在 `src/store/sync/`（`status / serverName / type / syncModeComponentId`，与 WebDAV 同步无关）。UI 桥在 `src/core/sync.ts`——注意它与 `src/core/sync/` 目录**同名共存**，`@/core/sync` 解析到这个文件，移动任何一方都会静默换义。

- **连接**：`client/index.ts` 的 `connectServer`（带 `connectId` 代次防竞态），流程 `parseUrl → handleAuth → socketConnect`。地址在设置页的 `IsEnable.tsx` 输入（校验 `^https?://`），历史地址存 `@sync_host_history`，当前地址 `@sync_host`。
- **三段握手**（`client/auth.ts`）：`hello`（GET `/hello` 校验魔术串 `Hello~::^-^::~v4~` 与协议版本 v4）→ `getServerId`（GET `/id`）→ 授权：`codeAuth`（授权码 → MD5 前 16 位作 AES 密钥，加密「authMsg + 本机 RSA 公钥 + 设备名」发 `/ah`，用 RSA 私钥解回 `KeyInfo` 并存档到 `@sync_auth_key`，按 serverId 区分）或 `keyAuth`（已存密钥复用认证）。加解密走原生桥 `@/utils/nativeModules/crypto`（AES-128-ECB 无填充、RSA-OAEP-SHA1，见 `plugins/sync/utils.ts`）。
- **长连接**（`client/client.ts`，297 行）：WebSocket，URL 带 `i=clientId&t=AES(msgConnect)`；心跳逻辑 `heartbeatTools`（服务端 ping 31 秒无响应关连接；断线重连等待 `min(2000 + ⌊failedNum/2⌋×3000, 30000)` ms；`maxTryNum = 100000`，实质是永不放弃重连；连接超时 2 分钟）。消息经 `createMsg2call`（RPC 超时 120 秒）分发到 `callObj`。
- **两个同步模块**（`client/modules/`）：`list`（歌单）与 `dislike`（不喜欢规则），`featureVersion` 均为 1，连接后按服务端支持集取交集启用。服务端可反向调用本机：`list_sync_get_md5`、`list_sync_get_sync_mode`（弹 `SyncModeModal` 让用户选合并模式）、`list_sync_get_list_data`、`list_sync_set_list_data`、`list_sync_finished`（置 ready 后才注册本地事件转发）。本地动作经 `plugins/sync/listEvent.ts` 适配转发，远端动作以 `isRemote=true` 回放防回声；转发失败即关连接（关闭码 4100）。
- **⚠️ 重要事实：消息「加密」已被掏空**。`client/utils.ts` 的 `encryptMsg/decryptMsg` 里 AES 实现整段被注释，现行逻辑是「消息 >1024 字符才 gzip 并加 `cg_` 前缀，否则明文发送」。即 (B) 的 WebSocket 歌单动作实际是明文（或 gzip）传输；只有握手阶段用真 AES/RSA。不要按变量名声称它端到端加密。

## 6.8 设计决策与历史教训

1. **opQueue 防丢三道闸**：`loadFailed` 标志 + `pendingOperations` 暂存 + `whenOperationQueueReady` 抛错中止。队列首次加载失败时，入队只暂存内存不落盘（落盘会用残缺队列抹掉存储里的旧操作），清队列在 `loadFailed` 时也直接跳过。
2. **failover 重跑与设置段错误上抛是配套设计**：`webdavSync.ts` 专门把 `syncSettingsAuto / syncUserApisAuto` 的错误从「内层吞掉记 warn」改为收集后抛出，否则 failover 永远感知不到设置段的连接失败。
3. **基线 hash 必须按合并后本地状态算**：见 6.3。`syncSettingsAuto` 与 `manualDownloadSettingsAndApis` 两处都按 `filterSensitiveSettingsForSync(settingState.setting)` 重算 `mergedHash`——改一处漏一处就会复发 ping-pong。
4. **候选被删的谎报坑**：`rotateToWorkingProfile` 里 `applyWebDAVServerProfile` 返回 null（候选已被删）时必须 `continue`，否则会拿上一台服务器的测连通结果谎报切换成功。
5. **两套体系对临时列表口径不一致**：(B) 的 list 模块对临时列表（`LIST_IDS.TEMP`）的 overwrite/remove/update_position 明确不外发，但 add/move 不过滤；(A) 则 tempList 照样进 playlists.json。如实记录，未统一。

## 6.9 一个运维提醒（非代码结论）

2026-10-25 真机曾出现：CloudDrive 后端上 `user_apis.json` 只有 76B 空文件、真内容（4.37KB）在同名 `.tmp` 文件里——那是 CloudDrive 服务端 PUT/MOVE 的暂存残留，不是本 App 写的（本 App 的临时文件后缀是 `.tmp-<随机>`）。**本地 user_apis 为空时不要直接点手动上传**，空文件会把云端唯一的好副本也覆盖掉；先在云盘 App 里把 `.tmp` 改名恢复，或先重建本地音源再上传。
