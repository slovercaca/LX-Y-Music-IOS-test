# 02 · 启动流程与运行时

> 本章回答一个问题：**从用户点开图标到主界面可用，代码依次做了什么、为什么是这个顺序**。涉及 `index.js`、`shim.js`、`src/app.ts`、`src/core/init/`、`src/navigation/` 与 `src/event/`。
>
> 状态管理（store）的细节在 [03 章](03-状态管理与数据持久化.md)；深链接的业务动作在 [10 章二改说明](10-本分支二改说明.md) 与本章 2.6 节。

---

## 2.1 入口链：三行代码，三层职责

```
index.js
  ├─ import './shim'        → shim.js：global.Buffer = require('buffer').Buffer
  └─ import './src/app'     → src/app.ts：真正的引导器
```

- `index.js` 里原 RNN 模板的 `registerComponent` / `setRoot` 代码整段被注释——屏幕注册与根布局都推迟到 JS 引导完成后由 `@/navigation` 完成（见 2.3）。
- `shim.js` 只有一行：给 Hermes 补 Node 的 `Buffer`。很多三方库（webdav、加密相关）默认 Buffer 存在，不垫这一步会在模块加载期就炸。
- `src/app.ts` 顶部副作用按顺序执行：导入 `@/utils/errorHandle`、导入 `@/config/globalData`（执行即装配全局对象，见 2.2）；DEV 构建下还会给 `React.createElement` 打补丁检测 undefined 组件、把 console 改写成带 `###RN_DEBUG_START###` 前缀的远程日志格式、给 `ErrorUtils.setGlobalHandler` 挂致命错误诊断。

## 2.2 全局对象装配（`src/config/globalData.ts`）

这是个纯副作用模块，import 即执行，做三件事：

1. 写 `process.versions.app = <package.json 的 version>`。
2. 初始化 `global.lx` 命名空间，字段包括：
   - `fontSize`（初始 0.9，后被真实值覆盖）、`isCarMode`、`restorePlayInfo`；
   - `playerStatus`：`{ isInitialized, isRegisteredService, isIniting, ignoreTrackPlayerLifecycle, userPaused, suppressUserPaused }`——播放器跨模块共享的运行时标志位都收在这里；
   - `apis: {}` 与 `qualityList: {}`：音源能力表，内置源与自定义源初始化时往里填；
   - `apiInitPromise`：`[Promise, true, resolver]` 三元组，供等待自定义源就绪的调用方使用；
   - `isEnableLog / isEnableSyncLog / isEnableUserApiLog` 等日志开关（由设置同步）；
   - `homePagerIdle`、`homePagerForceSync` 等 Home 页 PagerView 的协作标志（见 [07 章](07-界面层与导航.md)）。
3. 创建**四大事件中枢**并挂到全局：`global.app_event`、`global.list_event`、`global.dislike_event`、`global.state_event`（语义见 2.5）。

## 2.3 完整启动时序

```
① 垫片与全局装配（同步）
   index.js → shim.js → app.ts 顶部副作用：errorHandle、globalData
   → 四大事件中枢与 global.lx 就位

② 抢注启动事件（同步，必须抢先）
   app.ts 顶层立即 listenLaunchEvent()
   —— src/navigation/regLaunchedEvent.ts 用模块级 launched 标记 + handlers 队列
      解决「原生 AppLaunched 事件早于 JS 注册」的竞态：
      已 launched 时新注册的 handler 经 setImmediate 补发

③ 尺寸前置（并行，带兜底）
   Promise.all([ getFontSize(), windowSizeTools.init() ])
   各自经 withTimeout 包裹，失败用回退值不阻塞；结果写 global.lx.fontSize

④ 屏幕注册与导航初始化
   动态 import @/navigation → init(callback)：
   - registerScreens() 注册 13 个屏幕（每个都被 ThemeProvider 包装，见 03 章）
   - 注册 registerScreenPoppedListener → navigations.handleScreenPopped
   - 回调经 onAppLaunched 等待（或补发）原生 launched 事件后才执行

⑤ 核心初始化（回调内，严格顺序，见 2.4）
   handleInit() → initLog() → 动态 import @/core/init 并执行

⑥ 根界面落地
   navigations.pushHomeScreen() 执行 Navigation.setRoot（单 stack + Home）
   → Promise resolve 后 handlePushedHomeScreen()：
     cheatTip()；看设置 common.isAgreePact：
     - 已同意且首次 push → initDeeplink()（挂 Linking 监听、处理冷启动 URL）
     - 未同意 → showPactModal() 弹许可协议
   至此主界面可用
```

**每一步都有容错**：核心 init 的每步被 `withTimeout(..., 名称, 回退值)` 包裹，单步超时/失败降级为回退值继续；整体包在 try/catch 里，彻底失败才弹「初始化失败」对话框并 `exitApp()`。

**公告不在启动路径检查**：`core/init/index.ts` 注释明示现行策略——只在首次安装、用户签完协议后由 PactModal 触发一次（见 2.7 的脆弱点记录）。

## 2.4 核心初始化的内部顺序（`src/core/init/index.ts`）

顺序不是随意的，注释与依赖关系决定了它：

| 步 | 做什么 | 文件 |
|---|---|---|
| 1 | `commonActions.setFontSize(global.lx.fontSize)` | — |
| 2 | `initSetting()`：读/迁移设置并落盘，返回完整 setting 快照——**后续所有 init 都以这份快照为参** | `config/setting.ts` |
| 3 | `initTheme(setting)`：系统外观监听、状态栏同步、`applyTheme(await getTheme())` | `init/theme.ts` |
| 4 | `initI18n(setting)`：建 `global.i18n`，按 已存语言 → 设备语言 → `zh_cn` 定初始语言 | `init/i18n.ts` |
| 5 | `initUserApi(setting)`：挂自定义源脚本桥、读已装脚本列表（脚本真正 init 是异步事件驱动，见下） | `init/userApi/index.ts` |
| 6 | `initUiMode()`：原生 `getUiMode()` 返回 3（车机）时置 `global.lx.isCarMode` | `init/uiMode.ts` |
| 7 | `setApiSource(setting['common.apiSource'])`：内置音源就位 | — |
| 8 | `registerPlaybackService()`：注册 TrackPlayer 播放服务 | — |
| 9 | `initPlayer(setting)`：播放器装配（内部顺序见下） | `init/player/index.ts` |
| 10 | 后台串行链（`void` 异步，不阻塞主界面）：`dataInit(setting)` → `initDownloadPath(setting)` | `init/dataInit.ts`、`init/index.ts` |
| 11 | `initCommonState(setting)`：动态背景、Cookie 监听、日志开关同步 | `init/common.ts` |
| 12 | `initSync(setting)`（`void` 触发）：WebDAV 已配地址则 `triggerWebDAVSync()`；旧同步服务器开启且有 host 则静默连接，无 host 时自动关闭该开关 | `init/sync.ts` |
| 13 | `startCookieKeepAlive()` | — |

**`initPlayer` 的内部顺序**（`init/player/index.ts`）：`initPlayer`（挂 app_event 监听、启动即按 `player.cacheLimit` 执行缓存上限清理、应用音效配置）→ `initLyric`（歌词引擎；iOS 上把完整时间轴交给原生 `setNowPlayingLyrics`，由原生 NSTimer 驱动、锁屏不冻结）→ `initPlayInfo`（恢复上次播放：读 `@play_info` → 校验歌单与下标 → 加载为**暂停态**；`player.startupAutoPlay` 开时再延迟自动播）→ `initPlayStatus` / `initWatchList` / `initPlayProgress` / `initPreloadNextMusic` / `initPlayHistory` / `initRemoteCommand`。各文件的职责在 [04 章](04-播放核心与音乐数据.md) 展开。

**`dataInit` 做什么**（`init/dataInit.ts`）：`musicSdkInit()`；读用户歌单 → `setUserList`；读不喜欢规则 → `setDislikeInfo`；读下载任务 → `downloadActions.setTasks`（三者都经 `withInitTimeout` 兜底）；`cleanOneDriveDirtyData()`；三平台 Cookie 在场时拉一轮红心/关注/收藏（「我的歌单」索引按产品规则推迟到首次点开才拉）；恢复上次导航页（`setNavActiveId((await getViewPrevState()).id)` + `forceSyncNavActiveId()`）；删 `TEMP_FILE_PATH`。

**`initDownloadPath` 做什么**（`init/index.ts` 内）：iOS 下载目录四步迁移——旧默认目录改名为「本地」、Documents 里散落文件按下载任务记录迁移、坏路径修复、根目录文件按扩展名归位到 `music/ lrc/ picture/` 子目录，并写一次性标记键 `library_structure_migrated_notice`。

**`initCommonState` 与 `dataInit` 的分工**：dataInit 在 Cookie 监听挂上之前先拉一轮数据，initCommonState 随后注册三平台 Cookie 变更监听（`common.wy_cookie / tx_cookie / kg_cookie` 变化 → 重新拉取对应平台的红心/关注/收藏写入 user store；清空 Cookie 时清 store）——是「首拉 + 变更监听」的分工，不要以为是重复代码。它还负责动态背景封面：监听 `playerMusicInfoChanged` / `configUpdated`，`prefetch` 当前歌曲封面 → `setBgPic`；最近一次背景持久化在设置键 `theme.lastDynamicBgPic`，冷启动先行恢复防闪白。

**自定义源桥**（`init/userApi/index.ts`）：用户 JS 脚本运行在独立上下文里，靠事件桥与主 JS 通信。`onScriptAction` 分发原生侧事件（init/response/request/cancelRequest/showUpdateAlert/log）；主 JS 发起的请求经 `sendUserApiRequest` 以 `requestKey` 建 Promise 映射，20 秒超时；脚本 init 成功后按其声明的 `info.sources` 动态组装 `global.lx.apis[source].getMusicUrl/getLyric/getPic` 与 `global.lx.qualityList`（其中 getMusicUrl 会对脚本返回的 URL 发 HEAD 请求、用 content-length/content-type 反推真实音质）。脚本自己的 HTTP 请求走 `userApi/request.js` 的 `fetchData`（默认超时 13 秒，支持 abort）。

## 2.5 事件中枢：四条总线，四种语义

事件基类在 `src/event/Event.ts`：`listeners: Map<string, Function[]>`，`on/off/offAll/emit`。**派发语义必须记牢**：`emit` 先同步快照监听者数组，再用 `setImmediate` **异步**派发，逐个 try/catch 隔离异常（P0-2 修复：快照防订阅前事件误投递、异常隔离防一个监听者掐断后续全部）。推论：action 改完 state 后，组件刷新永远晚一个宏任务；同步读 state 永远是新值，但事件驱动的副作用不是即时的——大量 init 代码按此假设编排（例如 deeplink 的 nav 分支还要再叠 100ms setTimeout 等页面挂载）。

| 中枢 | 文件 | 语义 | 典型方法 |
|---|---|---|---|
| `global.state_event` | `event/stateEvent.ts` | **状态变了**（广播通知，约 40 个类型化方法） | `configUpdated(keys, setting)`、`themeUpdated`、`bgPicUpdated`、`playerMusicInfoChanged`、`playProgressChanged`、`mylistUpdated`、`navActiveIdUpdated`、`componentIdsUpdated`、`syncStatusUpdated`、`apiSourceUpdated`、`languageChanged`、三平台 `*LikedListChanged` 等 |
| `global.app_event` | `event/appEvent.ts` | **命令/动作**（约 60 个方法） | `play/pause/stop/error/playerEnded/setProgress/progressDragState/seekLyric/musicToggled/picUpdated/webdavPicUpdated/jumpWebDAVPosition/lyricUpdated/myListMusicUpdate/downloadListUpdate`、下载五件套、UI 类 `searchDeepLink/openSonglistImport/selectSyncMode/showArtistSelector/showPlaylist/showWebLogin` 等 |
| `global.list_event` | `event/listEvent.ts` | **歌单写操作中枢**：方法本身就是「改内存数据 + 落盘 + 广播」的一体化写路径 | `list_create/list_remove/list_update/list_update_position`、`list_music_add/move/remove/update/clear/update_position`、`list_data_overwrite`、`daily_rec_music_replace` 等 12+ 类 |
| `global.dislike_event` | `event/dislikeEvent.ts` | **不喜欢规则写操作中枢**（同上模式） | `dislike_data_overwrite/dislike_music_add/dislike_music_clear/dislike_changed` |

`listEvent` 的每个方法内部顺序固定：先调 `@/utils/listManage` 改内存数据 → 落盘（`saveUserList`/`saveListMusics`）→ 发 `app_event.myListMusicUpdate` → emit 自身事件；**非远程操作（`isRemote=false`）时还 `logOperation` 进 WebDAV 同步操作队列并 `markListsChanged()`**（见 [06 章](06-数据同步.md)）。它还含 `fixListIdType`（同步来的 number 型 id 转 string）与 `checkListExist`（活动歌单被删则回落 `LIST_IDS.DEFAULT`）。

`stateEvent` 用 `declare class EventType` 技巧让 `on/off` 获得按方法名推导的监听签名——订阅时能拿到每个事件的参数类型。

另有两个**模块私有**事件实例（不进全局）：`store/dislikeList/event.ts` 与 `store/userApi/event.ts`，只服务各自模块的 hook。注意 dislike 因此有「全局操作中枢」与「store 私有通知」两个同名概念、不同实例，`setDislikeInfo` 最终同时触达两者——改这块时先分清在跟谁说话。

## 2.6 导航机制（react-native-navigation）

- **注册**：`src/navigation/registerScreens.tsx` 用 `WrappedComponent` 把每个屏幕包进 `<Provider>`（实为 ThemeProvider，见 03 章），以 `Navigation.registerComponent` 注册 **12 个屏幕**。名字常量在 `src/navigation/screenNames.ts`（`lxm.*` 前缀）：Home、PlayDetail、SonglistDetail、Comment、PactModal、SyncModeModal、ArtistDetail、AlbumDetail、SimilarSongs、SettingDetail、AnnouncementModal、Toast。其中 8 个页面组件来自 `@/screens` 的 barrel 导出，4 个 overlay 组件来自 `navigation/components/`。（2026-11-12：独立 DownloadManager 屏幕已下线，下载任务并入「本地与下载」页的下载标签，见 07 章。）
- **根布局**：单 stack。`pushHomeScreen` 用 `Navigation.setRoot({ root: { stack: { children: [Home] } } })`，关 topBar、安全区 `safeAreaInsets` 恒为 always、Home 禁手势返回。Home 内部的多页切换走 PagerView + `navActiveId`（见 [07 章](07-界面层与导航.md)），**不走 RNN push**。
- **跳转**：业务代码调 `src/navigation/navigation.ts` 的 `pushXxxScreen(componentId, 参数)` 函数族，参数走 RNN passProps（歌单详情的 `info`、歌手/专辑信息、`settingId`、相似歌曲数组）。返回走 `navigation/utils.ts` 的 `pop/popToRoot/popTo` 薄封装。
- **弹窗不用 showModal，全部走 `Navigation.showOverlay`**：协议（PactModal）、同步模式（SyncModeModal）、公告（AnnouncementModal）、Toast（TOAST_SCREEN，非阻塞、定时自关，替代 iOS 上 `Alert.alert` 堆叠卡死）。关闭走 `dismissOverlay`（失败自动重试一次，防透明 overlay 残留拦截全屏触摸）。overlay 的关闭感知用 `navigation/event.ts` 的 `onComponentDidDisappear`——SyncModeModal 是 overlay，`modalDismissed` 事件永不触发，必须用 disappear 兜底。
- **JS 栈账本**：RNN 原生栈之外另维护一份 `commonState.componentIds` 账本：push 时由各屏生命周期写入，pop 时由 `registerScreenPoppedListener → handleScreenPopped` 删除并顺带释放 push 锁。这份账本被大量 hook 消费来判断「某页是否被覆盖/是否可见」，是省电门控（被覆盖的页面暂停玻璃渲染等）与状态栏同步（取栈顶 id 做 `Navigation.mergeOptions`）的共同依据。
- **启动事件竞态**：不用 RNN 的 `registerAppLaunchedListener` 直连，自建 `regLaunchedEvent.ts` 做标记 + 补发（见 2.3 步②）。

### push 防卡死三件套（真实事故换来的）

`navigation.ts` 的注释直言：RNN 自定义转场动画被打断时**永不回调 completeTransition、整栈卡死**。因此：

1. 全 App 的 push **不配置 animations**，走系统默认转场；设置详情页禁侧滑返回（`gestureEnabled: false`）；
2. `startPush` 做同顶拦截（另有 `allowSameTop`、`recoverStaleTop` 账本自愈策略），并加 **800ms 兜底解锁定时器**（pop 事件丢失会让 push 锁闩死、点击被静默吞掉）；
3. `guardPush` 保证 await 后必 `endPush`；
4. 进页前一律用 `getPushBackgroundColor` 定原生容器底色：优先取当前封面的缓存平均色（`getCachedBgPicColor`）、取不到回退主题色——原生容器底色与目的页模糊封面背景不一致，就是「进播放详情闪白」的原生侧根因。

## 2.7 深链接（`src/core/init/deeplink/`）

协议同意后才由 `initDeeplink()` 挂载：监听 `Linking` 的 url 事件 + 处理 `getInitialURL()` 冷启动链接。

- 链接格式 `lxmusic://<type>/<action>/...#params`，由 `index.ts` 的 `handleLinkAction` **手工字符串切分**（只在第一个 `#` 切、keyword 单独定位解析避免二次 decode——不用 `new URL()`，理由见 05 章 5.6 第 1 条）。
- type 分发：music / songlist / player / search / setting / nav。nav 的 search/songlist 分支先 `setPendingAction` 再 `setNavActiveId`，延迟 100ms 后发 app_event（等 PagerView 页面挂载，与 2.5 的异步派发语义配套）。
- 文件打开（file://、content://）由 `handleFileAction` 按扩展名分发：`.json/.lxmc` → 数据导入（`handleFileLXMCAction`）、`.js` → 自定义源脚本导入（`handleFileJSAction`）、音频文件 → 直接播放（`handleFileMusicAction`）。
- 各 action 文件：`musicAction.js`（`play`：校验后 `addTempPlayList` 插队并视情况 `playNext`，含跨源 `getOtherSource` 搜索匹配；`searchPlay`：按歌名搜索后播放；`search` 分支整段注释未生效）、`songlistAction.js`（仅 `play` 生效）、`playSonglist.ts`、`playerAction.ts`（play/pause/skipNext/skipPrev/togglePlay/collect/uncollect/dislike 直转 core/player）、`searchAction.ts`、`utils.js`（`dataVerify` 按规则校验外部数据的类型/长度/必填，`sources`、`qualitys`、`qualityFilter`）。

**安全口径**：深链接与文件导入都是外部输入，入口处都有 `dataVerify` 校验；改这块时不要绕过校验直接消费参数。

## 2.8 已知脆弱点（如实记录）

1. **公告/协议时序链**：PactModal 的 `scheduleAnnouncementCheckAfterPact` 用固定 400ms 等 overlay 关闭动画后才 `checkAnnouncement(false)`，并自承「期间应用被杀则靠下次启动已同意分支补检」；但 `init/index.ts` 当前已同意分支只调 `initDeeplink()`，补检落点未在本轮审计范围内确认。
2. **init 容错口径不统一**：主链每步有 withTimeout 回退，但 `dataInit` 与 `initDownloadPath` 在同一条后台串行链里、各自失败只记 bootLog——数据初始化失败时 App 照常进主界面，表现为「歌单/下载列表为空」，排查要看 bootLog 而不是崩溃日志。
3. **同名函数不同文件**：`setNavActiveId` 有两个版本——`store/common/action.ts` 的直改版（无同值短路）与 `@/core/common` 的封装版（dataInit、deeplink 用的都是后者，带同值短路且配 `forceSyncNavActiveId` 绕过）。改导航逻辑时极易改错文件。
