# 03 · 状态管理与数据持久化

> 本章讲 `src/store/`、`src/config/` 与全局设置的组织方式。先给结论：**这个项目不用 Redux/MobX/Zustand**——`store/Provider/Provider.tsx` 里的 redux Provider 与 `store/index.ts` 的 `useGetter` 都是整文件注释/空壳的历史残留。真正的机制是自研三段式：**模块级单例对象（state）+ 手写改值广播（action）+ 事件订阅桥（hook）**。

---

## 3.1 三段式模式

每个状态域是一个目录，统一三件套：

| 文件 | 角色 |
|---|---|
| `state.ts` | 模块级普通对象单例。任何代码可直接 import 读（如 init 层直读 `playerState.musicInfo.pic`） |
| `action.ts` | 唯一的写入口约定：函数直接改字段，然后手动调对应事件广播。没有 reducer、没有不可变约束，广播时按约定传 `{...state}` 副本 |
| `hook.ts` | React 桥接：统一模式为 `useState(读 state 初值) + useEffect(订阅对应事件 → setState)` |

事件总线见 [02 章 2.5 节](02-启动流程与运行时.md)：全局级是 `global.state_event`（状态通知）与 `global.app_event`（命令），外加带落盘副作用的操作中枢 `global.list_event` / `global.dislike_event`；dislikeList、userApi 两个域另有模块私有事件实例。

派发是异步的（`setImmediate`）：action 改完 state 后组件刷新晚一个宏任务。细粒度变体：`useSettingValue(key)` 只在变更 keys 含该键时刷新；`useProgress(autoUpdate)` 用 `isActive()` 门控，后台不 setState 省电。

### 关于「Provider」的名不副实

RNN 每个屏幕是独立的原生组件树、没有共同 React 根，所以 `registerScreens` 给**每一个**屏幕单独包一层 `<Provider>`。但 `store/Provider/index.ts` 导出的是 **ThemeProvider**——它只通过 React Context 提供主题（订阅 `themeUpdated` + rAF 后 setTheme）。其余全部状态不走 Context，靠单例对象在模块间共享，这也是跨屏幕状态不需要任何注入的原因。按名字找状态注入点会扑空，记住这一点能省很多时间。

| `songlist` | 与 leaderboard 同构（`listInfo` 默认 source 为 kw、limit 30） | 同样无 hook、无事件；`ListInfoItem` 类型被导航的歌单详情 passProps 复用 |
| `search` | `{ temp_source: 'kw'（类型被写死为字面量 'kw'）, searchType, searchText, historyList }` | 历史词去重 unshift、上限 15 条；落盘由调用方负责（旧版带节流落盘的实现整段注释在文件上半） |
| `search/music` | 每源一份 `{ list, total, page, maxPage, limit: 30, key }` + `'all'` | 单源 `setList` 去重合并分页；聚合 `setLists` 把多源结果按 `similar(keyword, 'name singer')` 相似度重排（bilibili 单源时跳过）；条目经 `toNewMusicInfo` 转换，失败记 log 并过滤 |
| `search/songlist` | 与 music 版同构（limit 15/18） | 单源分支补写 `state.maxPages`（注释：此前不写会导致上滑无限请求） |
| `announcement` | `{ showModal, announcementInfo, localAnnouncementId, status: idle/checking/error }` | `setAnnouncementInfo` 逐字段 undefined 守卫后广播副本 |
| `sync` | `{ status, serverName, type, syncModeComponentId }`——**旧同步服务器**的运行时状态，与 WebDAV 同步无关 | `setStatus/setMessage` 广播 `syncStatusUpdated`；`setServerInfo/setSyncModeComponentId` 不发事件 |
| `user` | 三平台在本 App 内的用户数据：wy（uid、红心 Set、关注歌手、收藏专辑/歌单、vip 类型）、tx（红心 Set、收藏歌单）、kg（红心 Set、收藏歌单） | action 为命名导出的一组 set/add/remove：id 一律 `String()` 归一化、add 前查重、变更后发对应 state_event；布尔 hook（`useIsWyLiked` 等）订阅 Changed 事件后重读派生值，带同值 bail-out；`setWyVipType` 不发事件 |
| `userApi` | `{ list, status: { status: false, message: 'initing' }, apis }`（命名导出） | 私有事件广播 `status_changed`/`list_changed`（传数组副本） |
| `version` | 只有 state.ts：`versionInfo{version（取 package.json）, newVersion, isLatest, ...}`、`ignoreVersion`、下载 `progress` | **无 action/hook**，写方在版本检查逻辑里（不在 store 内） |
| `soundEffect.ts` | 非三件套的独立文件：EQ/混响用户预设的内存缓存 + 持久化 | 写操作经 `runSerial` 串行化防快照覆盖；读失败直接抛错、不回退空数组（防 save 路径把预设误清空） |

**「哑 store」警告**：leaderboard、songlist、hotSearch、search 四个域的 action 不发事件、不带（或不全）hook，刷新完全依赖调用方在 await 后主动重读 state/返回值。在列表页这类长生命周期组件里这是数据过期重灾区，与 common/player 的事件驱动风格形成鲜明对照——改这些页面时先确认刷新路径。

## 3.3 设置系统（`src/config/`）

设置是全 App 最大的单例状态：一张**点号键**的扁平表 `LX.AppSetting`（如 `player.cacheLimit`、`sync.webdav.url`），默认值全量定义在 `src/config/defaultSetting.ts`（271 行，`version: '2.0'`），按域分组：`common.*`（含 wy/tx/kg/yt 四个平台 Cookie、六个日志开关、导航显隐与排序 `navStatus/navOrder/navFlatOrder` 等）、`player.*`、`theme.*`、`list.*`、`search.*`、`download.*`、`sync.*`、`other.*`。

### 合并规则（`config/setting.ts` 的 `mergeSetting`）

这段代码的每条规则都是被真实数据坑过后的针对性修复，改之前先理解：

- 原始类型键直接严格相等比较（防 `'18'` 这类字符串数值被判为未变更）；
- 七个深键做深比较且对象型逐键合并：`common.navStatus`、`common.navOrder`、`common.sectionExpandedStatus`、`common.navFlatOrder`、`common.discoveryPlatformOrder`、`search.enabledSources`、`list.myListVisibility`——防老数据缺新键时整键被旧值覆盖；
- **目标中不在当前设置集内的未知键显式丢弃**——防导入备份/同步下来的脏键污染设置表（这个项目有设置同步与备份导入，未知键丢弃是安全边界，不是洁癖）。

### 初始化与迁移（`initSetting()`）

1. 读 `@setting_v1`；存在则合并默认值后返回 `{ setting, updatedSettingKeys, updatedSetting }` 并落盘。
2. 缺失时读旧键 `@setting`，走 `migrateSetting.ts`（37 行字段映射表把 v1 前的嵌套对象映射成点号键）+ `migrate.ts` 的 `migrateListData()` / `migrateMetaData()`（旧歌单键、播放信息迁移，含时间字符串转秒）；迁移失败弹框并 `exitApp`——宁可不进 App，不能带着半迁数据继续跑。
3. 单键迁移：`player.autoPlayOnReturn` → `player.startupAutoPlay` 后删旧键。
4. 用 `NAV_MENUS` 权威表补齐 `navOrder/navFlatOrder` 的缺失项（新版本加了导航页时，老用户的顺序表要自动补位）。

业务代码改设置走 `@/core/common` 的 `updateSetting`（它在 store 的 updateSetting 之外还联动 WebDAV 同步的 `markSettingsChanged`、语言切换等，见 06 章）；store 层的 `setting/action.updateSetting` 只负责合并、广播、落盘。

### 其他配置文件

- `src/config/constant.ts`：全局常量总汇。`LIST_IDS = { DEFAULT: 'default', LOVE: 'love', TEMP: 'temp', DOWNLOAD: 'download', PLAY_LATER: null }`；`COMPONENT_IDS` 枚举（与 common store 的 componentIds 账本键对应）；`HEADER_HEIGHT = 42`、`LIST_ITEM_HEIGHT = 70`；`SPLIT_CHAR`（不喜欢规则的分隔符 `@`/`#`）；`NAV_MENUS`（17 个导航项 id+icon）；`NAV_COOKIE_GATED_IDS`（5 个需对应平台 Cookie 才显示的导航项）；`getEffectiveFlatOrder()`（扁平导航有效顺序：过滤废弃 id、去重、discovery 强制置顶、缺项补齐）；文件扩展名正则 `LXM_FILE_EXT_RXP`、`USER_API_SOURCE_FILE_EXT_RXP`；`MUSIC_TOGGLE_MODE`；以及 leaderboard/songList/search/viewPrevState 四组**不属于 AppSetting** 的独立默认值 `DEFAULT_SETTING`。
- `src/config/index.js`：仅导出两个资源——`defaultUrl`（`Silence02s.mp3`，播放器占位静音音频）与 `notificationIcon`。

## 3.5 设计决策与坑位汇总

1. **全量落盘设置**：`@setting_v1` 每次变更整表写。设置表不大，这个取舍换来的是「任何时刻落盘的都是完整一致快照」，导入/同步/迁移都简单；代价是高频改设置时写放大，靠上层节流（如下载任务的 1 秒节流是独立路径）。
2. **广播传副本、读直读单例**：action 广播时传 `{...state}` 防监听者误改；但任何代码都能 import state 直读——一致性靠「写必须走 action」的约定，没有运行时强制。
3. **同名不同物**：`setNavActiveId` 在 store/common/action（直改版）与 core/common（封装版）各一份；dislike 有全局中枢与私有事件两套；`Provider` 实为 ThemeProvider。这三处是新人最容易踩的命名陷阱，本指南在 02/03 两章都点了名。
4. **拼写遗产已成事实标准**：`@songist_setting`、`clearTempPlayeList`、`temp_source: 'kw'` 字面量类型——都已落盘或成为调用方依赖，不要单方面「修正」，要改必须带迁移。
5. **音效预设的读失败策略**：`soundEffect.ts` 读失败抛错而非回退空数组，因为它的 save 路径是「读全量 → 改 → 写全量」，回退空数组等于一次读失败就清空用户全部预设。同类「读-改-写全量」逻辑都应采用这个口径。
