# 04 · 播放核心与音乐数据

> 本章讲 App 的「大脑 + 喉咙」：点一首歌之后，代码如何决定去哪取链、取不到如何降质/换源、拿到 URL 后喂给哪个引擎播、歌词封面如何跟上、播完如何接下一首。涉及 `src/core/player/`、`src/core/music/`、`src/core/search/`、`src/plugins/player/`、`src/utils/musicSdk/`、`src/types/`，共约 3.2 万行。
>
> 先记住本章最重要的一条事实：**五大平台的「取播放地址」默认是空的**——SDK 里的 `getMusicUrl` 只是转发壳，真正的取链靠用户导入的自定义音源脚本（见 4.5）。搜索、歌单、排行、评论都是平台直连实现，与取链解耦，所以没导入音源时是「能搜能浏览、不能播」。

## 4.1 分层总览

```
UI（07 章）
  │  playList(listId, index) / playNext / togglePlay …
  ▼
core/player/        播放总控：队列语义、播放模式、取链编排、重试跳歌、
                    预加载、播放历史、进度时钟、锁屏同步、定时退出
  │  getMusicUrlInfo / getLyricInfo / getPicPath
  ▼
core/music/         取链仲裁：按歌曲类型四路分发（下载项 / 本地含 WebDAV /
                    汽水跨平台匹配 / 在线），在线走「本源→降质→换源」三段式
  │  apis(source).getMusicUrl …
  ▼
utils/musicSdk/     五平台 + Bilibili + 汽水的接口实现：
                    搜索/歌单/排行/评论/歌词/封面是真实现；
                    getMusicUrl 是转发壳 → global.lx.apis（自定义脚本）
  │
  ▼
plugins/player/     引擎层：统一引擎总线屏蔽双驱动差异；
                    TrackPlayer 驱动 + iOS 原生 FLAC 流式驱动；音效控制
  │
  ▼
原生（08 章）        TrackPlayer(fork) / StreamingFlacPlayerModule / NowPlayingModule
```

状态的唯一真相是 `store/player`（03 章），`core/player/playInfo.ts` 是它的门面。贯穿全链的数据对象是 `LX.Player.MusicInfo`（类型在 `types/player.d.ts` 与 `types/music.d.ts`）；下载任务形状的歌曲以 `'progress' in musicInfo` 区分。

## 4.3 双引擎与统一引擎层

这个 App 有**两个播放引擎**：

1. **TrackPlayer**（fork 版 react-native-track-player）：主力引擎，播 MP3/FLAC 文件与普通流。原生队列里实际只保留「当前真实轨 + 占位轨」，列表语义完全由 JS 层 store 维护（`getList` 对下载列表返回空数组，下载列表不走此路）。
2. **原生 FLAC 流式引擎**（`StreamingFlacPlayerModule`，08 章）：iOS 上播高音质 FLAC 时边下边解、直通实时 DSP。触发条件在 `nativeFlac.ts`：开关开启且音质属于 {flac, flac24bit, hires, master, atmos, atmos_plus}；本地 FLAC 文件已禁用此路、只用于远程流式。装载失败会回退到 AVPlayer 路径。

两引擎的事件经各自 driver 映射成统一事件汇入 `UnifiedPlayerEventBus`，上层（controller、进度、歌词）只订阅统一总线。原生 FLAC 激活时，`shouldIgnoreTrackPlayerLifecycle` 会让 TrackPlayer 驱动的生命周期事件被忽略——否则两个引擎的状态会互相打架。远程命令（锁屏/耳机）的 toggle 判定也以 `getUnifiedPlaybackState()` 的引擎真实状态为准（注释记录过「按两下才生效」的根因就是拿 JS 状态猜引擎状态）。

**为什么 WebDAV 歌曲要先整首下载再播**：iOS 的 AVPlayer 无法给请求注入 Authorization 头，带 Basic Auth 的 WebDAV 直链播不了——所以 `local.ts` 对 WebDAV 歌先走 05 章的原子下载到缓存，再以本地文件播。这是平台限制决定的设计，不是偷懒。

## 4.4 一次点歌的完整链路

```
1. UI 调 playList(listId, index)
   → setPlayListId + setPlayMusicInfo 写 store，派生 LX.Player.MusicInfo → play()

2. 取链仲裁（player.ts 的 getMusicPlayUrl）
   先试切换源歌曲本体（meta.toggleMusicInfo，不许再换源防递归），
   失败再走 core/music.getMusicUrlInfo 完整链：
   - 离线模式开 → 只查本地下载
   - 下载项 → download.ts（本地文件优先）
   - local → local.ts / localPlay.ts（WebDAV 预下载；本地无链时跨平台匹配）
   - qs 汽水 → localPlay.ts 跨平台匹配（汽水 SDK 本身没有取链）
   - 在线 → online.ts（见下）

3. 在线取链（online.resolveMusicUrl）
   URL 缓存（@music_url__）优先
   → 网易先补歌曲详情判 fee 与音质
   → preferApi 判定：
     · 非网易：恒走自定义音源脚本
     · 网易 VIP 歌 / 高音质 / 非 VIP 用户：走脚本，且失败不回退
     · 网易 + 有 Cookie + 普通歌：走 api-cookie 直连，
       按返回 level 映射真实音质（WY_LEVEL_TO_QUALITY）存缓存
   → handleGetOnlineMusicUrl 策略驱动（2026-11-12 起由「失败策略」模块编排，
     原写死的三段式「本源 → 降质 → 换源」已改为用户可排顺序/开关）：
     首选音质先试一次 → 按用户排的步骤顺序依次跑：
     · 换平台：getOtherSource 歌名清洗 → findMusic 跨源搜同歌（时长 ±5s + 六级
       优先级）→ 候选按用户平台优先级重排 → 递归到其他平台取链；
       retryedSource 防重复；URL 长度 <10 判失败
     · 换音质：本源按用户定的方向（往下/往上）一档一档走
     · 429 任何位置直通，不触发任何重试；总开关关闭时只试首选一次

4. 装载引擎
   setMusicUrl → plugins/player.utils.setResource（800ms 节流）
   → resourceLoader.loadPlaybackResource（loadGeneration 代际校验）
   → FLAC 高音质走原生引擎（失败回退），否则 trackPlayerCore：
     buildTracks 生成真实轨（+占位轨）add 进队列 → skip 到真实轨
     → seek 到恢复位置（pendingRestoreSeek 按「歌曲 id+切源 id」一次性绑定，
       防新歌吞掉旧歌的进度）→ play/pause → 清旧轨

5. 歌词与封面（与取链并行，同构三段式：缓存 → 本源 → 换源）
   歌词须过时间戳正则校验才认（防拿到假词）；网易无翻译时不用缓存
   封面可经 cacheCoverToLibrary 落盘到本地库 picture/ 全局缓存
   元数据经 delayUpdateMusicInfo 去抖后写锁屏：
   iOS 标题 =「歌名 - 歌手」、artist 位放当前行歌词、附真实速率与位置快照

6. 失败重试（两层）
   取链层：失败策略引擎编排（见第 3 步）；tooManyRequests 随机延迟 2–6 秒
           重试；在线歌曲不再有 player.ts 的盲目原样重试一次（策略引擎已覆盖），
           非在线路径仍保留；终态失败 5 秒后 playNext(true)
   引擎层：controller 25 秒加载看门狗（先同 URL 刷新一次）；
           错误三段恢复 = 按策略音质方向换质重试 → 同 URL 刷新 ×2 → 终态；
           设置 player.autoSkipOnError 开则 toast + 5 秒跳歌，关则只提示
   下载层：取链走同一策略引擎；文件阶段失败重取新鲜链接再下一遍（至多 2 次）；
           队列为并行工作池，同时 1–6 首可调（默认 3 首）
```

## 4.5 音源体系：SDK 与自定义脚本

### 平台注册表（`musicSdk/index.js`）

注册启用的源：**kw 酷我、kg 酷狗、tx QQ、wy 网易、mg 咪咕、bilibili、qs 汽水**，外加 local 本地源。`bd`（百度/太合）、`xm`（虾米）的实现文件在仓库里但**未注册**、不可达；`yt`（YouTube）实现存在但在注册表里被注释禁用。

### 取链的真相（再说一遍，因为最容易误解）

五大平台（kw/kg/tx/wy/mg）的 `getMusicUrl` 全部只是转发壳：经 `resolveQualityAlias` 做音质别名修正（如 userApi 模式下 hires→flac24bit，依据脚本声明的音质表）后，调 `musicSdk/api-source.js` 的 `apis(source).getMusicUrl`。而 `api-source-info.ts` 是**空数组**——没有任何内置取链后端。于是：

- 设置 `common.apiSource` 选中的是自定义脚本时，`apis()` 返回 `global.lx.apis[source]`（脚本在初始化时注册，见 02 章 userApi 桥与 08 章 UserApiModule）；
- 没有可用脚本时抛 `Api is not found`，播放直接失败。

**三条例外直连**（不依赖脚本）：

1. **Bilibili 自研直连**：`getCid` → `x/player/playurl`（fnval=16 取 DASH 音频），按音质 id（30216/30232/30280）选档、优先 mcdn 节点、固定按 192k 返回；它的 getPic/getLyric 是占位实现（歌词返回固定一句占位词）。
2. **网易 Cookie 直连**：`wy/api-cookie.js`，条件受限（见 4.4 第 3 步的 preferApi 判定），带重试与无版权回退。
3. **跨平台匹配链**（`localPlay.ts`）：本地/汽水/下载项需要在线链时，先问音源脚本，无脚本时回退到网易 Cookie 直连与 Bilibili 直连。

### 各平台 SDK 的真实现部分

搜索、歌单、排行榜、评论、歌手、专辑、每日推荐都是各源自有实现（走平台公开接口 + 各自签名），与取链解耦。歌词解密各显神通：

| 源 | 歌词 | 封面 | 签名/加密 |
|---|---|---|---|
| kw 酷我 | 私有格式：zlib inflate + GB18030 解码，逐字版再 base64 + `yeelion` 异或解密 | `pic.js` | getMusicInfo 走 kuwo.cn 接口 |
| kg 酷狗 | KRC 解码：逐字时间轴转换 + `[language:]` base64 提取翻译/罗马音 | `pic.js` | 登录走安卓端 MD5 签名（`utils/api.ts` 的 `signAndroidParams`）；CryptoJS AES + node-forge RSA（`utils/crypto.ts`） |
| tx QQ | QRC：三重 DES 解密（`qrc/` 三件，密钥为三段常量）后把逐字绝对时间换算为相对行首 | 有专辑 id 时直接拼 `y.gtimg.cn` 模板 URL | `zzcSign` 请求签名（`utils/crypto.js`） |
| wy 网易 | eapi 取词 | weapi 歌曲详情取 `al.picUrl` | weapi 双层 AES+RSA、eapi/linuxapi（`utils/crypto.js`，底层走原生 CryptoModule 的同步方法） |
| mg 咪咕 | MRC：TEA 解密（BigInt 密钥表，`utils/mrc.js`） | `pic.js` | — |

聚合能力在 `musicSdk/index.js`：`searchMusic` 跨源聚合搜索（单源 10 秒超时兜底——注释指出部分平台搜索无 timeout 会连带卡死跨平台匹配）；`findMusic` 跨源同歌匹配（时长 ±5 秒 + 六级优先级 + 多轮排序），是换源与跨平台匹配的共同底座。

## 4.6 队列、播放模式与进度

- **播放模式**五种：`listLoop`（列表循环）、`random`（随机）、`list`（顺序播完停）、`singleLoop`（单曲循环）、`none`。选下一首由 `getNextPlayMusicInfo` 按模式 + 已播过滤决定；**手动**点下一首时，list/singleLoop/none 会被改写为 listLoop 语义（用户手动切歌就是想继续听）。random 模式有 `randomNextMusicInfo` 预取缓存（连取链和歌词一起预取），重置点分散在切歌/模式变更/列表变更处。
- **稍后播放**：`tempPlayList` 优先于列表顺序消费（03 章 store/player）。
- **切歌防竞态三重串行化**：actionId、promise 链、代际令牌（`loadGeneration` 等）——双引擎 + 异步取链下，旧歌的迟到回调打到新歌是这类 App 的头号 bug 源，本项目在装载、元数据（`metadataSeq`）、恢复（stale 检查）三处都设了代际校验。`nativeFlac.ts` 写状态前两次校验 `currentTrackId`（注释标注 2026-10-05 引擎-P1-3：无校验时 reloadConfig 的 restore 会 wipe 新代际状态、致暂停键失灵）。
- **预加载**：controller 收到 playing 后触发 `preload.ts`：对下一首预取 URL（允许换源）+ 歌词，最多试 5 首、确定性 404 立即停、`attemptedIds` 去重；开关 `player.isEnableAudioPreload`。另有 init 层的 `preloadNextMusic.ts` 做引擎侧的 URL 预热与可达性校验（02 章）。
- **进度时钟**：`audioClock` 锚点外推供歌词/进度条高频读取（避免每帧过桥），约 1 秒由原生位置重锚校准；seek 走 `seek.ts` 的梯度轮询收敛，**未收敛不重发 seek**（重发会取消在途 seek、搅动缓冲），靠 playing 事件重锚自愈，并带切歌守卫防旧 seek 打到新歌。
- **时长以引擎为准**：`getTimelineDuration` 优先引擎真实时长、元数据 interval 仅兜底（曾有元数据 03:30 vs 实际 03:48 的错位实锤）。
- **播放历史**：init 层监听达标（满 120 秒或比例过半）后调 `playHistory.ts` 落库：promise 串行队列写入、同歌同日去重、上限 5000 条 / 31 天，写后发 `playHistoryUpdated` 并标记 WebDAV 待同步（06 章）。

## 4.7 音效系统

JS 侧在 `plugins/player/soundEffect/`：`soundEffectController` 聚合能力、`buildCurrentConfig/applyCurrentConfig` 组装全量配置，唯一适配器 `nativeEqualizerAdapter` 把配置下发原生 SoundEffectModule（08 章）；原生侧的实际 DSP 引擎是注入 track-player 的 `LXEqualizerAudioMix.swift`（10 段 biquad EQ、相位声码器变调、峰值限幅、空间声像、卷积混响，09 章补丁第 9 条）与 AppDelegate 内的 C++ 卷积内核。内置 13 个卷积 IR wav（`soundEffect/assets.ts`）。参数的单一事实源是 `config/soundEffectDspProfile.json`，由 `scripts/check-sound-effect-dsp.js` 守与原生双实现逐值一致。注意：声像与变调按产品定案**恒定下发复位值**（UI 可以调，实际不生效——以 controller 代码为准，不要按设置项臆测行为）。用户 EQ/混响预设的持久化在 store/soundEffect.ts（03 章）。

## 4.9 设计与坑（代码证据）

1. **取链单点**：整个 App 能否播放系于 `common.apiSource` 选中的那个脚本。排障时先确认脚本已导入且被选中，再怀疑别的。
2. **远程命令双通路**：`service.ts` 明确注释——RemotePlay/Pause/Next/Prev 已由原生 MPRemoteCommandCenter 处理（经 UtilsModule 的 `remote-command` 事件进 JS，见 02 章 remoteCommand），service 只接 RemoteDuck/RemoteStop。两边都接就会双触发跳两首。
3. **锁屏元数据的字段复用与两个真机坑**：iOS 把当前行歌词塞进 artist 字段（车机/蓝牙只读得到它）；`updateCurrentTrackMetadata` 注释记录 RNTP 整包重发元数据会擦掉歌词、传空 artwork 会清封面——故 iOS 元数据只走原生 NowPlayingModule、且 artwork 无值时干脆不带这个键。
4. **占位轨的平台差异**：`buildTracks` 的占位轨（URL 以 `//default` 结尾）主要服务非 iOS 的队列连续性；iOS 无 URL 时不加占位轨、有 URL 时只加真实轨。`utils.ts` 的 `isEmpty/isTempId` 靠正则识别占位轨。
5. **音质回显不可信的历史**：旧版 `getMusicUrlInfo` 回显请求档位会误判 FLAC 高精度路径，现由 `resolveOnlineMusicUrl` 返回**实际**音质；网易 Cookie 路径靠 level 反映射存缓存。同类问题在 Bilibili 直连也修过（固定 192k 却回显请求音质致上层误标缓存）。
6. **SDK 返回形状不统一**：各源返回 Promise 与 `{ promise }` 两种形状并存，`resolveSdkResult` 最多解包 3 层来抹平；新接一个源时先确认它的返回形状。
7. **seek 不重发原则**（与 08 章歌词时钟配套）：梯度轮询只观测、不重发，靠事件重锚自愈——「seek 后歌词冻住/乱跳」类问题先查锚点与守卫，别先想着重发 seek。
